Scotri, white-label

Scotri is a read-only analysis agent for data platforms. It takes a ticket or a question, traces it across pipelines, notebooks, semantic models and live data, runs read-only tests, and hands back a work order a human can act on. One engine serves any number of organisations: its rules live in code, and everything specific to one client lives in a single profile file and the knowledge pack generated from it.

What every deployment gets

From a ticket to a handoff, without touching production

Each engagement runs the same lifecycle. A bug that turns out not to be a bug stops at stage 2, with the verdict as the deliverable. Nothing past stage 7 is code; a person applies any change by hand.

  1. IntakeRestates the ticket and lists gaps and ambiguities.
  2. Bug verdictConfirmed, not a bug, or inconclusive, with a root-cause category and confidence.
  3. Impact analysisBlast radius across every repo in the registry, seeded from a lineage graph generated from the mirror after every sync (ADF trigger to report, down to measures and RLS roles), and checked against live data.
  4. PlanWhat to change, in what order, with risk and alternatives.
  5. Tests, executedSQL and DAX assertions run read-only; real pass or fail recorded.
  6. ProposalOptional .patch in proposals/, applied by a person.
  7. HandoffOne document, Bug or Story template, for the implementer.
  8. Jira writeComment, Bug or attachment, shown to the user first.

Query governor

Every outbound call is rate-limited per user, capped per backend, cached and audit-logged. A rejected call reports a real queue position or wait.

Prod mirror

Prod branches are read from a local read-only mirror refreshed by a separate sync service, with freshness verdicts and a maintenance flag.

Team memory

Each investigation ends with a learning (mechanism, not numbers) that the next one retrieves. People review verdicts; overturned ones drop out of retrieval.

Answer check

Every table name, file and large number in a final answer is matched against the run's own tool results. Anything unsupported goes back to the agent.

Three ways in

A REST API for a web UI, an MCP server for other agents, and a CLI. All three share one queue and one set of rules.

Operations

Admin panel for queue, logs, mirror sync and caller apps. Every admin action is audited; access fails closed.

White-label model

What stays fixed, and what each client brings

The work splits into three layers. The core is the product. Adapters are chosen per technology stack. The client pack is the only part that names a business. It lives in the client's own repo, generated from one profile file, so upgrading the engine never touches it.

Core · same for every client

Rules and lifecycle

  • Query guard: SELECT-only allowlist, one statement per call
  • Governor policy: rate, concurrency, cache, audit
  • Tool scope: what an unattended run may read, write and execute
  • Secret redaction on every output and every Jira write
  • Engagement lifecycle, admission queue, cancel and timeouts
  • Grounding check, learnings, verdict review, retention

Client pack · per organisation

What makes it theirs

  • One profile: repos, catalogs, Jira projects, factories, model (client/profile.yaml)
  • Generated from it: registries and client config (services/config/*.yaml) and facts docs (docs/ai/client/)
  • Domain knowledge a person writes: conventions, lineage, platform-map notes, optional report documents whose KPI definitions reach kpi-lookup (skeletons in docs/ai/client/)

Hexagonal architecture

One core, connected only through ports

Business rules sit in the centre and import nothing but the Python standard library and each other. They talk to the world through 30 port modules, each a small typed interface. Adapters implement those ports for a specific technology, and a single composition root picks which adapter fills each port. A test fails the build if any core module imports a vendor SDK, Redis or the app layer.

Inherited by every client

Guardrails enforced in code, not by instruction alone

The agent is told the rules, and each one below is also enforced by code it cannot change. A new client gets all of them on day one.

No write credential exists for any product repo, on the agent or the sync service.

SQL is SELECT-only: a leading-keyword allowlist, a single-statement check and a write-verb denylist, behind a SELECT-only service principal.

Tool scope hook: an unattended run may write only to its output folders, run only the governed CLI, and cannot read secrets or the unredacted mirror.

Redaction on every CLI output, every published deliverable and every Jira write.

Run identity: every call is attributed to the real caller from a run token, whatever user name the agent passes.

Ceilings on wall-clock time, turns and cost per engagement, plus a bounded queue per user.

Deploying for a new client

Onboarding, in order

Each client gets a private repo created from this template. For a client on the same stack (Azure DevOps, ADF, Databricks, Fabric, Jira), every step is a setup command or writing. A different stack adds adapters behind the existing ports. SETUP.md lists the exact permissions each service account needs.

  1. Describe the client

    python -m app.setup init writes client/profile.yaml: repos and Prod branches, catalogs, Jira projects, factories, which optional components exist, and the name users see. examples/acme-retail/ is a complete worked profile.

  2. Generate config and docs

    python -m app.setup render writes the registries and client config, and the facts docs under docs/ai/client/. Generated files are rebuilt on every render; skeleton docs are created once and then belong to the client.

  3. Add credentials

    python -m app.setup secrets collects read-only service principals, a read-only git token and a Jira account into the gitignored services/.env, with input hidden.

  4. Check every connection

    python -m app.setup doctor checks Redis, Azure DevOps, Databricks, Jira, Fabric and ADF, and names what is missing.

  5. First sync

    python -m app.setup bootstrap runs the first mirror sync and builds the lineage index; from then on every sync regenerates the lineage and the onboarding platform map (/platform-map).

  6. Write the knowledge pack and run the benchmark

    Fill the conventions and lineage skeletons, set governor limits and roles, then replay a few known tickets with tools/benchmark/ before opening it to users.

Readiness

What is still open

White-labelling works today: the engine carries no client names, and the answer check reads its catalog names from the client config. These items remain before a production rollout.

The governor's backend list is fixed to the Microsoft data stack. A new stack needs a new entry alongside its adapter.

small · code

Production sign-in must be configured per client (open item #57): an Entra app registration and roles. Dev auth is for local use only.

config

Engagement history and the admin audit log are SQLite and files on one host (open item #15). Multi-replica hosting needs the Azure SQL/Postgres adapter.

medium · adapter

Webhook and scheduled-sweep triggers are not built yet (open item #7), so every run today starts from a person or another agent.

medium · code

One deployment serves one client, from its own repo. Several clients on one host would need client-scoped storage keys and caches, which this design does not include.
