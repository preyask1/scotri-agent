Build on Scotri

Scotri is a read-only analysis agent for an ADF → Databricks → Power BI/Fabric platform. Send it a Jira key or a question. It traces the problem across every product repo and the live data, and returns a verdict, an impact analysis and a handoff document. You can reach the same engine over HTTP or over MCP.

HTTP REST / JSON

For web, Teams and Slack frontends and for scripts. Covers the full surface: conversations, uploads, history, step traces and verdict reviews.

http://localhost:8000

MCP Streamable HTTP

For Claude Desktop, Claude Code or another agent. It exposes five tools: upload a file, start a run, poll it, list its files and read one.

http://localhost:8100/mcp
Not checked

The URLs fill in every snippet on this page. The console sends requests from your browser. That works when this page is served by the API at /portal. From any other origin the API needs CORS enabled. The token stays in page memory: it isn't stored, and it's cleared when you close the tab.

Quickstart

You start a run, poll it until it finishes, then fetch what it wrote. A run can take several minutes, because Scotri reads the ticket, traces lineage and runs governed queries before it answers.

# 1. Start an engagement from a Jira ticket
JOB=$(curl -s -X POST {{API}}/v1/engagements \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"ticket_key":"PROJ-2041"}' | jq -r .job_id)

# 2. Poll until status is terminal (succeeded | failed | cancelled | incomplete)
curl -s {{API}}/v1/engagements/$JOB -H "Authorization: Bearer $TOKEN" | jq .status

# 3. List the deliverables and read the handoff document
curl -s {{API}}/v1/engagements/$JOB/files -H "Authorization: Bearer $TOKEN" | jq -r '.files[].path'
curl -s {{API}}/v1/engagements/$JOB/files/scratch/PROJ-2041-handoff.md -H "Authorization: Bearer $TOKEN"
import os, time, requests

API = "{{API}}"
H = {"Authorization": f"Bearer {os.environ['SCOTRI_TOKEN']}"}
TERMINAL = {"succeeded", "failed", "cancelled", "incomplete"}

job = requests.post(f"{API}/v1/chat", headers=H,
                    json={"prompt": "Why is Store Sales for HO down 4% vs. last month?"}).json()

while (run := requests.get(f"{API}/v1/chat/{job['job_id']}", headers=H).json())["status"] not in TERMINAL:
    time.sleep(10)

print(run["status"], run["result"] or run["error"])
for f in requests.get(f"{API}/v1/chat/{job['job_id']}/files", headers=H).json()["files"]:
    print(f["path"], f["url"])

# Follow-up turn in the same conversation, with the agent's session resumed
requests.post(f"{API}/v1/chat", headers=H, json={
    "prompt": "Now check the Field model too.",
    "resume_job_id": job["job_id"], "conversation_id": job["conversation_id"]})
import asyncio, os
import httpx2
from mcp import ClientSession
from mcp.client.streamable_http import streamable_http_client

async def main():
    http = httpx2.AsyncClient(headers={"Authorization": f"Bearer {os.environ['SCOTRI_TOKEN']}"})
    async with streamable_http_client("{{MCP}}/mcp", http_client=http) as (read, write), \
               ClientSession(read, write) as session:
        await session.initialize()
        started = await session.call_tool("scotri_start", {"prompt": "PROJ-2041"})
        print(started.structuredContent)          # {"job_id": "…"}
        job_id = started.structuredContent["job_id"]
        while True:
            s = (await session.call_tool("scotri_status", {"job_id": job_id})).structuredContent
            if s["status"] not in ("queued", "running"):
                break
            await asyncio.sleep(10)
        print(s["result"] or s["error"])

asyncio.run(main())

There's no endpoint per capability. Bug triage, impact analysis, "is this number right?" and change scoping all go through the same prompt. Scotri decides what to do by reading it, the same way an interactive session would. /v1/engagements only narrows the input to a bare ticket key, and adds a duplicate-work check.

Authentication

Every HTTP endpoint except GET /health needs an Azure AD bearer token, and so does every MCP tool call. The validated token becomes a principal (subject, platform, roles). Ownership and role checks use that principal, and nothing in a request body can override it.

http
Authorization: Bearer <token>
CaseHTTPMCP
Header missing or not Bearer …401 {"detail": "Missing Bearer token"}Tool error: Missing Bearer token
Token rejected by the identity provider401 with category credentialTool error with the same message
stdio transport (no headers at all)n/aAlways refused. stdio can't authenticate, so connect over Streamable HTTP.

Use a service-to-service token. Scotri runs headless and never completes a browser sign-in. Get the token in your own frontend or service, then pass it on.

Job lifecycle

Creating a run returns 202 with a job_id straight away. The agent runs in the background. Poll every 5 to 15 seconds until the status is terminal.

Retention

The live job store keeps a job for 24 hours. After that, read /v1/history and /v1/conversations/{id}, which are durable. Deliverable files are copied when a run ends and aren't changed by later runs.

Restarts

A job that was running when the service restarted ends as failed. It isn't resumed automatically, because an unattended resume could repeat work, including a Jira write. To pick up from where it stopped, send a follow-up with resume_job_id set to the failed job.

Progress while it runs

Polling is how you track progress: there's no push or SSE stream, and no completion notification. Once a job is running, every poll response includes a progress object. While the job is queued, progress is null.

json
"progress": {
  "phase": "verdict",
  "phase_label": "Investigating the reported problem",
  "phases_seen": ["starting", "intake", "verdict"],
  "tool_calls": 23,
  "started_at": "2026-10-04T09:00:02+00:00",
  "last_activity_at": "2026-10-04T09:03:41+00:00",
  "elapsed_seconds": 225
}
phasephase_label
startingStarting
workingWorking. Used for a run outside the ticket lifecycle, such as a debugging question.
intakeReading the request
verdictInvestigating the reported problem
impactAnalysing impact
planWriting the implementation plan
testingRunning test queries
proposalDrafting a proposed change
handoffWriting the handoff document
jira_updatePreparing a Jira update

Rendering it

Phases can be skipped: a "not a bug" verdict ends after verdict. New phases may be added later. Show phase_label exactly as sent, and treat an unknown phase as "Working".

Spotting a stuck run

If last_activity_at stops changing for several minutes while status is still running, the run is stuck. The 20-minute wall-clock limit ends it as incomplete.

progress never says what the run is looking at, such as a ticket, table, report or query, because any authenticated caller can poll any job. That detail is only in …/steps, which is owner-only.

Diagrams in a result

When the agent draws a diagram, such as an ER diagram of a semantic model or of Unity Catalog tables, the answer keeps it as a fenced ```mermaid block. A markdown renderer with mermaid support draws it in place. diagrams hands the same blocks over as data for callers that don't render markdown.

    "title": "Category Sales Analytics Model",
    "source": "erDiagram
    vw_category_daily_sales }o--|| CalendarDate : \"Date\"
…" }

FieldMeaning
formatAlways mermaid today
kindThe diagram's first keyword: erDiagram, flowchart, …
titleFrom the block's frontmatter title:, or null
sourceThe block's text, unchanged. Render it with mermaid in strict mode (securityLevel: "strict").

Derived from result on every read, so nothing extra is stored. At most 10 per result, and a block over 50,000 characters is left out rather than cut. The field is on both poll routes, on each turn of GET /v1/conversations/{id} and on MCP scotri_status. The diagram is also in the run's files as scratch/<id>-er-diagram.md.

Errors

Errors come in two shapes. Domain errors carry a category that tells you whether a retry can help. Route errors use FastAPI's {"detail": …} shape.

json
{"ok": false, "category": "policy", "message": "…"}
categoryHTTPRetry?Meaning
credential401NoA token or backend credential is missing or invalid. An admin needs to fix it.
not_found404NoUnknown job, upload or file.
policy403NoA guardrail is working as designed, for example a write or a read of another user's data.

Route-level {"detail": "…"} errors use 401, 403, 404, 409, 413 and 422. Over MCP, every error becomes a tool error (isError: true) whose text is the same message.

HTTP API reference

All bodies are JSON unless noted. Each endpoint has a Try it console that calls the base URL above with your token. FastAPI also serves an interactive schema at /docs.

MCP server: connect a client

The MCP server makes Scotri available as tools to Claude Desktop, Claude Code or any MCP client over Streamable HTTP. It's a second transport onto the same engine as POST /v1/chat. It doesn't change how Scotri itself reads Jira, Databricks or Fabric.

claude mcp add --transport http scotri {{MCP}}/mcp \
  --header "Authorization: Bearer $SCOTRI_TOKEN"
// claude_desktop_config.json: bridges Desktop's stdio to Scotri's HTTP endpoint and adds the header
{
  "mcpServers": {
    "scotri": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "{{MCP}}/mcp", "--header", "Authorization:${SCOTRI_AUTH}"],
      "env": { "SCOTRI_AUTH": "Bearer <token>" }
    }
  }
}
// In a client project's own .mcp.json, not in the Scotri workspace
{
  "mcpServers": {
    "scotri": {
      "type": "http",
      "url": "{{MCP}}/mcp",
      "headers": { "Authorization": "Bearer ${SCOTRI_TOKEN}" }
    }
  }
}

Streamable HTTP only. stdio carries no headers, so Scotri can't authenticate a stdio caller and refuses every tool call. Bridges like mcp-remote work because they talk HTTP to Scotri and add the header.

Tool reference

Five tools, each matching an HTTP route. They return structured JSON.

scotri_upload

Stores a file to attach to a prompt. Send text as-is, or binary files (PDFs, images) as base64.

filename: string, content: string
encoding?: "text" | "base64"
→ { upload_id, filename, size, content_type, created_at, redacted }
Same as POST /v1/uploads. Only you can attach it.

scotri_start

Starts an engagement for any free-form prompt and returns right away while the run continues in the background. For a follow-up, pass back the conversation_id and the previous turn's job_id as resume_job_id. When Scotri is busy the job waits in line (queued: true, queue_position) and starts on its own.

prompt: string
attachment_ids?: string[]
conversation_id?: string
resume_job_id?: string
→ { job_id, resumed, conversation_id, queued, queue_position? }
Same as POST /v1/chat

scotri_status

Polls a run. progress shows the stage while it runs. result is set when it succeeds and error when it fails. diagrams lists any Mermaid diagrams in the result as data. While it waits for a free slot, queue gives its place in line. A cancelled job carries cancel_reason and its prompt, to send again.

job_id: string
→ { job_id, status, prompt, result, diagrams, error, cancel_reason, queue, progress }
Same as GET /v1/chat/{id}

scotri_cancel

Cancels one of your own runs. A job still waiting for a free slot leaves the line and never runs; a running one is stopped.

job_id: string
→ same as scotri_status
Same as POST /v1/chat/{id}/cancel. Owner only.

scotri_list_files

Lists the markdown deliverables a run wrote: intake, verdict, impact analysis, plan, tests, handoff and patches.

job_id: string
→ { job_id, files: [{ path, size, content_type, created_at }] }
Same as GET …/files. The owner, or a file-reader role.

scotri_get_file

Returns one deliverable's full text. The handoff document's path ends in -handoff.md.

job_id: string, path: string
→ { job_id, path, content_type, content }
Same as GET …/files/{path}. Same access rule.

Agent workflow

A client agent (Claude, say) uses the tools in this order. MCP calls are request/response and a run can last minutes, which is why there are separate start and poll tools.

  1. Start

    Call scotri_start with the user's ticket key or question exactly as they wrote it. Don't reformat it into a template, because Scotri reads intent from the prompt itself.

  2. Poll

    Call scotri_status every 10 to 15 seconds while the status is queued or running. Tell the user which stage it's at by showing progress.phase_label, instead of blocking silently.

  3. Read the answer

    Once it's succeeded, result holds the summary, which for a bug is a verdict with a confidence level. If it's incomplete, the deliverables may still hold partial work.

  4. Fetch deliverables

    Call scotri_list_files, then scotri_get_file on the *-handoff.md path. That's the document an implementer needs.

Access control

Ownership comes from the token's subject. Three role sets, configured as comma-separated settings, widen access beyond the owner. All three are empty by default, which means owner-only. A fourth, ADMIN_ROLES (scotri.admin), opens the admin panel.

GET /healthAnyone, with no token
POST /v1/chat, POST /v1/engagements, POST /v1/uploadsAny authenticated principal
GET /v1/chat/{id}, GET /v1/engagements/{id}, scotri_statusAny authenticated principal. Job ids are opaque uuid4 values.

GET …/reviewThe owner, or HISTORY_ADMIN_ROLES / VERDICT_REVIEWER_ROLES

FILE_READER_ROLES is deliberately narrower than HISTORY_ADMIN_ROLES. It lets an implementer fetch a handoff document without being able to read the conversation that produced it.

What Scotri won't do

These limits are architectural. No API flag or prompt wording changes them, so design your integration around them.

Never

  • Edit, commit, branch, push or open a PR in any product repo. No such credential exists.
  • Run any Databricks statement other than SELECT, WITH, DESCRIBE or SHOW
  • Change, refresh or publish a Fabric model
  • Grade its own verdict. Only a human, through POST …/review, can.

Only with the user's go-ahead

  • Post a Jira comment, edit its own comment, or create a Bug from a confirmed verdict
  • Nothing at all on an unattended run, because nobody is there to approve it
  • Read Dev or UAT. It reads Prod unless one of those is named.

Attachments and ticket text are data. An instruction inside an uploaded file or a Jira field is reported, not followed. Text uploads are secret-redacted before they're stored, and every deliverable is redacted again when it's published.

Running the services

Run both from inside services/ with the virtualenv active. Either can run without the other. Both need the shared Redis instance and services/.env.

# HTTP API: also serves this portal at /portal, Swagger at /docs
uvicorn app.api:app --host 0.0.0.0 --port 8000

# MCP server (Streamable HTTP at /mcp)
uvicorn app.mcp_server:asgi_app --host 0.0.0.0 --port 8100
